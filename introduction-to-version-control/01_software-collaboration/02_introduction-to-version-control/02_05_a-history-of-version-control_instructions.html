As you know by now, version control is a system that records changes to a file or set of files over time so that you can access specific versions later. In software development, Version Control Systems (VCS) allow developers to manage changes to their code and track who made each change. But how did these systems come about?

Version control has a long history, with its earliest foundations beginning in the 1970s alongside the birth of modern computing. Over the decades, version control has evolved through two major architectural phases: Centralized and Distributed systems.

The Era of Centralized Version Control

Early version control systems relied on a centralized model. This means that all file operations and version histories were stored on a single central server. If developers wanted to work on a file, they had to "check it out" from this central location.

  • RCS and CVS: In 1982, Walter F. Tichy created the Revision Control System (RCS). A few years later, in 1986, Dick Grune developed the Concurrent Versions System (CVS) to build upon RCS's foundation. CVS stored information about every file in a folder structure, including its location, who last modified it, and when. While popular for many years, CVS had significant design flaws. It lacked integrity checks, meaning network errors could result in corrupted files being accepted into the system. It was also designed primarily for text files, making it poor at handling binary files like images or videos.

  • Subversion (SVN): To solve the glaring issues in CVS, CollabNet developed Subversion (SVN) in 2000. SVN introduced vital data integrity checks and vastly improved the versioning of binary files. SVN became highly popular in the open-source community, with Google and SourceForge offering free hosting. However, SVN was still a centralized system. If the central server went down or the network was slow, development was completely blocked.

The Rise of Distributed Version Control

To solve the bottleneck of centralized servers, Distributed Version Control Systems (DVCS) were created. In a distributed system, every developer downloads (clones) the entire history of the project directly to their local computer, meaning they can work offline and independently without relying on a single central server.

The shift to distributed systems was largely driven by the development of the Linux kernel:

  • BitKeeper: Initially released in 2000, BitKeeper was a proprietary (paid) distributed VCS used by the Linux kernel team. In 2005, the company behind BitKeeper revoked the free license it had provided to Linux creator Linus Torvalds. This controversy sparked the immediate creation of two new, free open-source alternatives: Mercurial and Git.

  • Mercurial: Created in 2005 by Olivia Mackall, Mercurial was designed as a high-performance distributed VCS. It featured a small learning curve, making it incredibly popular for former SVN users looking to transition to a distributed system.

  • Git: Also created in 2005, Git was developed directly by Linus Torvalds specifically to host the massive Linux kernel source code. Git is renowned for its speed, branching capabilities, and distributed design.

Understanding the Difference: Git vs. GitHub

Today, Git is the undisputed industry standard for open-source and proprietary software projects. However, people often confuse "Git" with "GitHub." It is vital to understand the difference:

  • Git is the actual software system/command-line tool installed on your local computer that tracks your code changes.

  • GitHub (along with alternatives like GitLab and Bitbucket ) is a cloud-based hosting company that allows you to store your Git repositories online so you can easily collaborate with other developers.

In short: Git is the tool; GitHub is the hosting service.
